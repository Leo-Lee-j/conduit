**Conduit 能力扩展调研 · 2026-11-10**

已确认范围：不开发“项目运行与验证”。其余表格能力纳入实施范围；不依赖新增运行管理器，运行预览仅处理已有链接与产物。Diff 交互详见[功能设计说明](run-and-review-design.md)。下文竞品资料与投入估计是原调研依据，不代表功能已交付。

当前已实现入口及未完成边界见[项目工具](project-tools.md)。尤其 WSL/SSH 目前只提供交互终端，文件检查点目前是单文件文本恢复；不能把这两项当作完整远程工作区和全项目快照。

建议把下一阶段重点放在“任务组织、上下文交接、审查交付”：让用户能清楚地知道每个任务改了什么、验证到了哪一步，以及还差什么才能交付。优先实现任务工作区与 Diff 审查反馈。这是基于当前实现和官方产品资料的产品判断，尚未经过用户访谈或使用数据验证。

本次基线为本地 `Cargo.toml` 的 0.3.2、Git 提交 `473c29b`。先通过 CodeGraph 定位实现，再查阅项目文档和必要的未覆盖代码；外部资料直接核对官方页面正文。未启动应用做界面验收，未运行竞品，也未验证账户、套餐或地区可用性。下文“未发现”仅表示本次检视范围内未发现完整产品入口，不代表对应 CLI 或 MCP 不能完成这项工作。

任务工作区与审查反馈先形成可验收的基础。

1. **任务工作区首版：把任务和已有隔离能力连接起来。** 新建任务选择现有工作区或创建 worktree，保存目标和验收清单，关联一个或多个会话；提供运行、待审查和完成状态。完成后提供归档与显式清理入口。先支持单仓库，允许用户继续使用现有普通会话，不强制迁移历史。验收时至少覆盖两个任务分别修改同名文件、重新启动后关联恢复，以及脏 worktree 不被误清理。[R2][R3][R4]

2. **审查首版：把意见绑定到具体修改。** 支持审查未提交变更或相对基线分支的变更；行级评论保存文件、版本及定位信息，变更漂移后标记过期。用户可以选择另一个引擎检查修改，把发现项送回原任务修复。审查输出需有具体触发条件、影响和位置；无法结构化的输出保留原文，不伪造“审查通过”。首版做好反馈和问题状态，分块暂存/撤销可以随后加入。[R5][S3][S8]

实现时有几处约束会直接影响产品设计。

- **worktree 已有创建入口，但并发交付仍有互斥。** `worktree_has_runs` 按共享 repository scope 判断运行任务，分支写操作会等待同仓库任务结束。首版应明确显示等待原因；未来若要让一个 worktree 提交时另一个继续运行，需要按操作研究锁粒度，不能简单移除现有保护。[R11]
- **Git 暂存策略影响分块审查。** 当前常规刷新会自动暂存已跟踪修改，主动移出暂存也可能被下一次刷新重新暂存。引入分块选择前，应先定义手动选择与自动暂存如何共存，否则用户刚选择的提交范围可能被刷新改变。[R4]
- **CLI 能力不完全对等。** 任务模板、命令、会话分支和恢复应显示实际可用能力；不同引擎之间交接的是可审阅的摘要与材料，不能承诺无损迁移内部原生上下文。[R1][R8][R9]
- **用量统计要区分已知、未知和估算。** 现有会话最后一次 Usage 不应直接当成完整逐日账单。应先建立来源和去重规则；金额依赖价格及计费方式，缺失时显示未知。建议首版做提醒，只有能可靠控制执行时才提供硬预算限制。[R7]
- **验证要绑定版本。** 同一个工作区里的测试通过记录，不能在后续修改后继续代表当前结果。最低限度需要记录运行所对应的提交和工作区变更指纹。
- **恢复要说明覆盖面。** 对话恢复、已跟踪文件、未跟踪文件和外部命令产生的副作用是不同范围。可先在任务 worktree 内提供明确基线的恢复预览，再扩展跨会话恢复。[S4]
- **本地自动化受应用生命周期约束。** 应用未运行、机器睡眠和重启后的任务状态都要明确；首版可要求应用运行，记录错过的触发，不默默补跑可能修改文件的旧任务。[R2][S2]

可以穿插交付的较小改进有四项：选中代码/终端输出后附到聊天草稿、带来源的会话 Markdown 导出、项目常用提示模板、统一待处理视图。最后一项应复用已有通知中心，把待审批、等待回答、失败和待审查任务集中展示，避免另建一套通知系统。[R5][R6][R12] 这些属于建议，仍需在实施前核对当前具体交互与数据模型。

建议按三个阶段推进，不预设具体周数。

| 阶段 | 交付范围 | 判断是否值得继续的依据 |
| --- | --- | --- |
| 第一阶段 | 行级审查反馈、任务与现有 worktree 绑定、项目预设与上下文交接 | 从执行完成到开始审查是否更快；是否减少手动找目录和复制日志 |
| 第二阶段 | 任务归档、PR/CI、跨引擎交接、用量汇总 | 任务是否更容易完成交付；检查失败到修复验证的耗时是否缩短；交接后是否频繁补充遗漏上下文 |
| 第三阶段 | 定时任务、受控检查点；按用户需求选择 WSL/SSH 或更完整的运行预览 | 自动化结果是否被实际使用；失败与恢复是否可解释；远程环境需求是否来自足够多的目标用户 |

建议先用 5–8 位经常同时使用两个以上编程助手的 Windows 开发者验证排序，观察他们完成真实修复任务的过程。重点记录手动切换窗口、重复复制上下文、等待 Git 操作、寻找验证结果和清理工作区的次数。此样本只用于发现交互问题，不能据此推算市场规模。使用数据应由参与者知情提供。

完整编辑器/LSP、自建云执行集群、复杂多代理依赖图、广泛可执行插件市场可暂缓。这些方向需要更大的持续维护投入；先通过任务、交接和审查功能验证用户是否愿意把 Conduit 作为日常主工作台。现有原生贡献机制可继续支撑内置界面扩展，可执行插件的生产准入问题应按既有文档单独推进。[R10]
