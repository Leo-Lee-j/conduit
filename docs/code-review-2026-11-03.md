## 发现

### 1. [P1] 移出暂存可能同时修改未选中文件的暂存状态

位置：[src/git.rs:1020](../src/git.rs#L1020)，对照暂存路径的 [src/git.rs:965](../src/git.rs#L965)。

`Operation::Unstage` 调用 `git restore --staged --pathspec-from-file=... --pathspec-file-nul`，缺少暂存操作已经使用的 `--literal-pathspecs`。NUL 分隔解决参数分隔和引号问题，仍允许 Git 的 pathspec 通配匹配。

已在隔离仓库复现：同时暂存 `file[1].txt` 和 `file1.txt`，路径文件只包含 `file[1].txt`，当前命令将两个文件都移出暂存。加入 `--literal-pathspecs` 的对照命令仅移出选中的文件。这会改变下一次提交包含的内容。

建议：暂存和移出暂存共用 literal pathspec 执行辅助函数，补充包含方括号文件名及未选中匹配文件的回归测试。工作区文件内容在本次复现中未被修改，但索引选择错误是确定的。

### 2. [P1] 后台导入的旧快照可以覆盖扫描期间完成的新对话

位置：[src/app/sessions.rs:1042](../src/app/sessions.rs#L1042)、[src/app/sessions.rs:1080](../src/app/sessions.rs#L1080)、[src/history.rs:107](../src/history.rs#L107)。

扫描在后台读取历史，合并时只过滤此刻仍在 `runs` 中的会话。扫描某个会话后，如果该会话开始并完成了新一轮对话，合并时运行已从 `runs` 移除，旧快照就会通过过滤；`merge_session` 随后直接执行 `existing.messages = messages`。

启动页超时后允许交互，以及添加工作区后的异步导入，都使这条时序可达。结果可能是刚完成的回复、错误或取消记录被旧历史替换，后续正常保存还会将替换后的内容写入状态文件。仅检查“当前是否运行”无法证明快照仍然有效。这项结论来自静态调用链，未做完整 UI 时序复现。

建议：扫描开始时记录每个会话的 revision；合并时 revision 变化就跳过或重新扫描。导入应明确区分 CLI 可重建的消息与 Conduit 自己保存的审批、错误及完成信息，避免将导入快照无条件当作全部状态的权威来源。

### 3. [P2] 已保存的手动会话名会被自动历史导入覆盖

位置：[src/history.rs:100](../src/history.rs#L100)、[src/app/sessions.rs:240](../src/app/sessions.rs#L240)。

用户手动重命名后，标题会保存到 Store；但已有会话导入时，只要 CLI 导入标题非空，就无条件赋给 `existing.title`。Claude 导入标题通常由第一条提示词生成，因此重新启动自动导入即可将用户命名恢复为提示词摘要。取消正在运行的 AI 命名任务只能保护当前操作，不能保护下一次历史导入。

建议：持久化标题来源或用户覆盖标记。导入标题只填补空标题，或只更新仍由导入管理的标题。补充“手动命名 → 保存 → 导入同一 native ID”的测试。

### 4. [P2] 历史替换后，消息大纲缓存可能保留失效的键和位置

位置：[src/app/outline.rs:29](../src/app/outline.rs#L29)、[src/app/outline.rs:105](../src/app/outline.rs#L105)、[src/app/sessions.rs:1093](../src/app/sessions.rs#L1093)。

`MessageOutlineCache::refresh` 只在会话 ID 改变或消息数量减少时清空缓存。历史导入会重建消息键并可能改变分段，消息数量相同或增加时，旧缓存仍被视为有效。点击旧键时，`jump_to_message` 在新消息中找不到它，直接返回；缓存位置和文字也可能与新内容不一致。

已通过保留当前 refresh 和生成条目算法的独立探针复现：同一会话将一条 `live-user` 消息替换为一条 `import-0` 消息后，缓存仍保存 `live-user`，无法在当前消息中找到。该探针验证算法，不替代完整 UI 测试。

建议：为 transcript 增加 revision，缓存以 `(session_id, revision)` 判断整体替换；保留追加路径的增量处理。在历史整体替换时同时核查列表测量、消息跳转等依赖消息键和位置的状态。

### 5. [P2] 保存整个 Store 会同步阻塞 UI 线程

位置：[src/app.rs:760](../src/app.rs#L760)、[src/store.rs:407](../src/store.rs#L407)、[src/app/runtime.rs:463](../src/app/runtime.rs#L463)。

`persist` 从 UI 回调和 poll 直接调用 `Store::save`。保存将所有工作区的完整会话序列化为 pretty JSON，分配完整输出缓冲，写入并 `sync_all`，再进行 write-through 替换。活跃对话约每秒触发一次，收到 native ID、任务完成和多个用户操作还会立即触发。

因此一次很小的字体设置或消息变更，其代价也随全部历史数据增长。大历史、慢磁盘或杀毒软件介入时，这条路径会延迟输入、布局和事件消费；原子替换保障完整性，却不能保障 UI 响应速度。

建议：引入单一后台保存执行器，按 revision 合并待保存请求，并通过完成回执清理对应版本的 dirty 状态。快照应采用可共享或增量的结构，避免把完整深拷贝留在 UI 线程。中期将设置与会话记录拆开持久化；关闭窗口需要等待最新版本保存成功或明确处理失败。

### 6. [P2] 流式事件仍反复遍历整段历史，削弱消息索引优化

位置：[src/app/runtime.rs:875](../src/app/runtime.rs#L875)、[src/app/events.rs:71](../src/app/events.rs#L71)、[src/app/sessions.rs:72](../src/app/sessions.rs#L72)。

消息索引已经将按键查找变为增量处理，但每次 `apply_event_indexed` 返回修改位置后，仍调用 `attach_turn_model` 遍历全部历史消息；模型字段早已填写时也不会跳过扫描。`session` / `session_mut` 同时从所有工作区的会话中线性定位目标。

单批 E 个事件、目标会话 H 条历史消息、总会话 S 个时，仅这些操作就有约 `O(E × (H + S))` 的工作量。1000 个事件和 10 万条历史消息意味着模型附加路径可能执行约 1 亿次条目检查，这不是实测耗时，但说明代价取决于历史规模。

建议：只对 `changed_index` 对应的 Assistant 消息设置模型；模型后到时只补扫当前轮的范围。为会话建立稳定 ID 到位置的索引，统一维护增删和工作区重排时的更新。

### 7. [P2] 事件队列没有背压，poll 的事件数量上限不能约束总体工作量

位置：[src/chat_runtime.rs:203](../src/chat_runtime.rs#L203)、[src/chat_runtime.rs:458](../src/chat_runtime.rs#L458)、[src/app/runtime.rs:526](../src/app/runtime.rs#L526)。

后台到 UI 使用无界 `mpsc::channel`。UI 每轮从每个运行取最多 1000 个事件，而非全局时间或字节预算。并行运行数增加时，一次 poll 的总体工作量随之增加；单条事件的负载也不相同。生产速度持续高于 UI 消费速度时，队列和完成事件等待时间会增长。

建议：先合并同一消息连续 Delta，再为所有运行设置公平的全局消费预算。事件传输应有字节或容量限制，且在设计背压时保证取消、审批和完成消息仍可送达；直接换成阻塞发送可能把进程清理与 UI 消费相互卡住，需要一起设计。

### 8. [P2] 每次历史导入都会完整读取并解析不相关的 CLI 历史

位置：[src/history.rs:41](../src/history.rs#L41)、[src/history.rs:232](../src/history.rs#L232)、[src/history.rs:459](../src/history.rs#L459)。

批量扫描已经避免按工作区重复读取，是有效优化；但它仍遍历全部 Claude / Codex 历史，将每个 JSONL 完整 `read_to_string` 并解析，然后才分配给匹配的工作区。读取没有单文件或累计大小限制，也没有取消参数和基于修改时间的增量缓存。

长期使用 CLI 后，即使当前工作区历史很少，启动成本仍随整个用户历史库增长。超时释放启动页只释放 UI 门控，并不会停止扫描。大型 JSONL 还会同时保留原始文本和解析后的消息。

建议：先读取小段元数据筛选 cwd；使用有界、逐行读取；缓存文件身份、大小及修改时间，只处理新增或变化文件。将取消和过大历史的可见反馈贯穿扫描。不要通过截断后静默替换现有完整消息解决内存问题。

### 9. [P2] 搜索在渲染路径对全部历史进行重复扫描和分配

位置：[src/app/search.rs:161](../src/app/search.rs#L161)、[src/app/search.rs:228](../src/app/search.rs#L228)、[src/app/search.rs:17](../src/app/search.rs#L17)。

搜索结果在 dialog content 渲染时同步计算，逐条消息 `to_lowercase().contains(query)`。40 个结果的限制只约束输出数量；无匹配或稀有关键词仍需扫描全部历史。提取 snippet 时还会建立全文大小的小写映射和字符数组，尽管界面只展示一小段内容。

建议：按查询和 transcript revision 缓存结果，对输入做短 debounce，较大的检索放到后台并丢弃过期结果。定位第一个命中后只处理附近的字符窗口。保留现有 Unicode 边界处理，不要用简单字节偏移替代。

### 10. [P2] CI 和发布检查没有覆盖 feature-gated UI 测试

位置：[.github/workflows/ci.yml](../.github/workflows/ci.yml)、[.github/workflows/release.yml](../.github/workflows/release.yml)、[src/app.rs:782](../src/app.rs#L782)、[src/app/files.rs:1953](../src/app/files.rs#L1953)。

工作流只运行默认 feature 的 Clippy 和测试，而大量并发、草稿、文件导航及更新 UI 测试需要 `ui-tests`。因此默认检查通过不能证明这些测试能编译或通过。

建议：增加启用 `ui-tests` 的编译检查和确定性的 UI 回归任务，按耗时分组；真实 CLI 或需要模型额度的测试继续保持 opt-in。另外，[src/history.rs:1482](../src/history.rs#L1482) 的断言 `result.is_empty() || result.iter().all(|_s| true)` 恒为真，并读取真实用户历史，应改为隔离的历史目录 fixture 和具体期望。

## 架构与代码风格

1. **应用状态的职责边界需要继续收敛。** `ConduitApp` 虽然分散在多个文件中，仍集中持有聊天、导航、Git、审批、搜索、设置、缓存和保存状态；`poll` 从 429 行延伸到 956 行，混合了调度、业务转换、持久化及视图失效。拆文件改善了定位，但没有缩小状态修改的边界。建议先将 Git 状态收敛为完整的 `GitUi`，再分离会话控制器和保存服务；顶层负责协调，子视图订阅所需 revision。

2. **关键状态值得类型化。** 审批、工具运行状态目前跨模块以“等待中”“运行中”“输出中”等字符串参与业务判断。建议在领域层使用 enum，将 wire 字符串转换放在协议边界，将中文显示放在 UI 边界；序列化时显式兼容旧状态。这比简单把字符串移动到 constants 文件更能防止非法状态。

3. **共享契约优先于大规模样式清理。** `Operation::Stage` / `Unstage` 的验证、路径文件创建、写入和清理有明显重复，本次 literal pathspec 差异已经体现出维护成本。抽取这类包含不变量的辅助函数很有价值。运行入口的九个参数可收敛成请求结构。逐步减少 `use super::*`，让每个模块依赖显式；不建议仅按文件长度拆分 UI builder 或集中所有布局数字。

4. **保留已经做好的实现。** `MessageIndex` 的增量查找、可见行测量、文件读取和语法高亮的后台执行、文件大小/行长限制、Mermaid 的容量限制与串行渲染、Windows Job 清理屏障、损坏状态防覆盖、更新清单和安装包验证都值得继续保留。Mermaid 的最多 12 条缓存线性查找属于有界小集合，本次未将它视为性能缺陷。
