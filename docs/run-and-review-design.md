# Diff 审查反馈设计

用户已排除“项目运行与验证”，不实现运行配置、命令管理器、检查执行器或运行日志系统。其余能力按调研表推进。

当前已实现本地行级评论、版本关联、处理状态、已查看标记、附到指定会话草稿、当前文件只读 AI 审查及结构化发现导入、PR 行级讨论快照与本地同步，以及 CI 失败检查转修复任务。全仓库审查快照、评论自动重新定位和向 PR 写回尚未实现。

以下描述长期交互目标，实际可用范围以 [Git 工作流](git.md) 为准。

**Diff 审查反馈，建议先让人工反馈准确落到代码，再接入 AI 审查。**

入口直接放在现有 Diff 页：文件列表可标记已查看，代码行支持添加评论，旁边提供反馈列表和“审查当前修改”。已查看状态属于对应文件版本；该文件变化后需要重新查看，其他未变化文件可以保留状态。

首版审查范围建议提供“全部未提交修改”和“相对指定分支的修改”。前者包含适用的已暂存、未暂存和未跟踪文本文件；后者应固定选定基线和目标版本。二进制、过大或未能完整读取的文件需要在审查覆盖范围中说明。范围由用户选择，不把整个工作区的修改自动归因给当前助手。

人工反馈的典型操作如下：

1. 用户在 Diff 的新增行或删除行选择一个范围，添加意见，例如“这里需要覆盖空输入，并补一条测试”。这是交互示例，不是对现有代码的缺陷判断。
2. 评论保存在本地，附带文件、左右侧、行范围、原始片段和对应版本；关闭标签或重启后仍可找到。
3. 用户勾选若干意见，点击“附到聊天”，选择当前会话或新的会话。
4. 草稿附上意见编号、上下文片段和处理要求，用户发送后才启动修复。
5. 助手回复修改完成时，意见进入待复核；用户检查新 Diff、运行相关检查后，再标记解决或继续讨论。

AI 审查可以使用当前引擎，也可以由另一个引擎执行。建议默认建立独立的审查会话，保存审查范围、说明和输出，并保持原修改会话可继续使用。不同引擎的审查入口由能力适配决定；当前命令目录并未完整接入所有原生审查操作，具体能力以[命令当前交付](chat-commands.md)为准。

每条 AI 发现尽量包含：问题标题、优先级、文件和定位、触发条件、行为影响、建议的验证方式。模型提供的路径与行号需要校验；无法可靠定位的发现保留为独立意见，不能硬贴到错误的代码行。缺少结构化结果时仍保留原始审查正文，不把解析失败当成没有发现问题。

建议把审查意见的处理状态和定位状态分开：

| 维度 | 建议状态 | 作用 |
| --- | --- | --- |
| 处理 | 待处理、已发送修复、待复核、已解决、不采纳 | 表达用户对意见采取了什么动作；不采纳时可记录理由 |
| 定位 | 适用于当前版本、已重新定位、原版本已变化、无法定位 | 表达意见是否还准确对应当前代码 |
| 审查覆盖 | 完整读取、部分读取、未检查、执行失败 | 防止把“没有返回发现”当成“全部审查通过” |

例如助手在某行上方插入十行后，评论不应仅靠旧行号移动。应结合原始片段、Diff 变更块和文件版本尝试重新定位；只有唯一可信匹配时才显示新位置，否则保留原位置并提示复核。文件删除或重命名也不能自动证明问题已解决。

AI 审查应明确其读取的版本。首版可以在工作区稳定时捕获审查快照；模型还需要读取周边源码时，应使用一致的快照或在执行期间监测变动并将本次结果标为过期。只有 Diff 文本固定、其他源码继续变化时，不能宣称审查面对的是完全一致的代码版本。

审查意见与 Git 操作应在交互上清晰区分：标记意见已解决、标记文件已查看，都不自动暂存或丢弃代码。分块暂存/撤销可作为后续能力。当前常规刷新会自动暂存已跟踪修改，引入分块选择前需要先确定它与自动暂存的关系，见[Git 工作流](git.md)。
