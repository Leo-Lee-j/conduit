# 内存优化评估（待确认）

状态：仅记录候选方案与体验取舍，尚未批准或实施。后续由用户确认具体范围后再修改实现。关联约束见[性能与指标](../performance.md)。

## 目标和边界

优先减少确定不再使用的资源，以及明显超出显示需求的图片数据。涉及画质、滚动流畅度和切换速度的调整，必须单独评估，不以降低这些体验作为默认优化手段。

本次依据是 2026-11-17 Windows 开发版进程的一次内存调查。原进程 PID 29524 已退出；进程页基线采于 17:15:35（UTC+08:00），随后对同一进程进行了只读堆和 D3D11 纹理检查。采样不是暂停后的原子快照，不能将结果视为当前版本的持续占用或正式性能基准。

- 系统堆混合包含应用、系统库和图形组件的分配，以及堆内空闲空间；尚无分配调用栈，不能将其全部归为聊天记录或缓存。
- 三块独立读写分配分别常驻约 28.5、7.1、1.1 MiB，所有者尚未确认，不能预先认定它们可以回收。

## “图片”具体指什么

这里指进程内识别到的一张 **2910×1334 的四通道解码位图**，与三缓冲、MSAA 等窗口绘制缓冲分开统计。

CPU 侧数据长度为 `2910 × 1334 × 4 = 15,527,760` 字节，约 14.8 MiB；对应分配包含页对齐后约 14.816 MiB。GPU 侧另有相同尺寸的 BGRA8 纹理。两侧尺寸吻合，符合图片解码后上传的情形，但尚未通过对象所有者或资源标识确认二者对应同一业务对象。

**尚不知道画面内容、文件名或所属功能。不能将它直接称为壁纸、聊天附件、截图或预览图，也不能判断它是否已不用。** 当前默认数据目录中的壁纸设置为关闭，但该设置不是原始采样时的状态快照。

本次只读检查了仓库 `assets`、默认数据目录的 `attachments` 和 `wallpapers`：分别识别到 51、28、5 个可读取的图片文件，没有恰好为该尺寸的文件。这个检查不覆盖其他数据目录、外部文件、网络或内存生成内容；尺寸也可能经过缩放，因此无法排除上述任一业务来源。

后续应先记录图片资源标识、解码尺寸、显示尺寸、持有者及移除时机，再通过打开/关闭相关内容观察生命周期。图片来源明确之前，不实施针对这张图片的降采样或强制释放。

## 候选方案与体验取舍

以下收益均是按上述窗口或图片尺寸计算的条件估算，不代表进程常驻量会等额下降；方案之间存在重叠，不能直接相加。

| 候选方案 | 可能收益 | 用户可能感受到的变化 | 前提与建议 |
| --- | --- | --- | --- |
| 释放确定不用的图片及其图集引用 | 取决于实际存活资源；该尺寸图片 CPU 数据及 GPU 逻辑像素各约 14.8 MiB | 若稍后重新使用，可能增加解码、上传等待 | 优先调查持有关系；保留近期常用内容。CPU 副本还可能用于重传或设备重建，不能直接删除 |
| 按显示需求解码、上传图片，并保留按需加载清晰版本的能力 | 假设宽高均减半，CPU 数据和 GPU 逻辑像素各减少约 11.1 MiB | 处理不当会导致高 DPI、放大查看时变糊或出现加载等待 | 来源、显示物理像素尺寸及放大需求明确后评估；不能统一降低图片分辨率 |
| 路径中间纹理按需创建或按实际区域分配 | 当前两张纹理合计约 68.0 MiB，实际可省量取决于路径使用与覆盖区域 | 理想情况下画面相同；实现不当会造成裁剪、闪烁或首次绘制卡顿 | 延迟创建仅在尚未使用路径时有收益；按区域分配需处理坐标、裁剪、复用和窗口缩放，成本较高 |
| 路径抗锯齿从 4×MSAA 调至 2× | MSAA 纹理逻辑量减少约 27.2 MiB | 曲线、斜线、部分图标边缘可能出现更多锯齿；不等于所有文字都会变糊 | 有明确画质取舍，需用户确认接受范围，并验证采样支持与截图；暂不作为默认调整 |
| 三缓冲改双缓冲 | 少一张窗口缓冲，约 13.6 MiB 逻辑量 | 某些设备、负载下可能影响呈现等待及滚动、动画流畅度 | 暂缓，除非有原生呈现和交互测试支持 |
| 收紧图集、会话或渲染缓存 | 未知 | 切回旧会话、滚动至旧内容时可能重复加载、解码或计算 | 先测利用率、命中率和淘汰效果。当前图集已有空位复用及整张无引用回收；不能把纹理容量全部视为浪费 |

会话缓存的当前目标是 8 个已加载正文、估算 64 MiB，并保护选中或运行中的内容，见[实现](../../src/app/transcripts.rs)。这些是淘汰策略参数，不能作为已占用字节或保证可节省字节。

## 建议顺序与待确认项

1. 补齐图片和独立大块的资源归属，区分仍在使用、近期复用和确实过期的资源。
2. 在保持清晰度和功能的前提下，评估过期资源释放、图片显示尺寸与解码尺寸匹配。
3. 评估路径中间纹理按需分配；缩小区域的实现需单独设计。
4. 只有用户明确接受画质或缓存行为取舍后，才试验降低 MSAA、减少缓冲或收紧缓存。

当前所有候选方案均待确认。尚未确定实施项目、性能目标、可接受的画质变化或缓存等待范围。

## 后续验证要求

- 使用同一源码基线、构建 profile、数据、窗口物理尺寸和 DPI，对照基线与候选实现。开发版单次调查不代表正式版收益。
- 分别记录进程 Working Set、Private Commit、GPU SharedUsage 与纹理逻辑字节。它们有交叠或语义差异，不合并为一个总数。
- 资源释放后同时观察提交量和生命周期；工作集下降可能只是页面不再驻留。本次两次采样中写合并页常驻量约从 159.9 降至 78.9 MiB，提交量仍约 159.94 MiB，不能据此报告资源已释放。
- 检查浅色/深色、不同 DPI、窗口缩放、曲线和细线边缘、图片放大，以及滚动、切换会话和重新打开图片。若改变 CPU 图片保留策略，还要验证设备重建后的恢复。
- 报告完整帧/交互延迟及首次加载等待，并执行独立进程重复对照；不能只凭内存数字改善宣称体验保持不变。
