# P3：安装管理、存储与发布验收

设计版本：0.2；日期：2026-11-04；状态：待实现。前置：所选 [P2-A Shell](phase-2-shell-runtime.md)或 [P2-B 独立进程](phase-2-local-runtime.md)，以及[共同约定](README.md)。本阶段把显式开发加载形成用户可操作、可恢复的本地插件管理流程。

## 后端适用范围

本阶段只实现 P2 已选定的一个后端。安装注册表、包摘要、启用偏好、scope、数据代次和升级回退为共用约定；以下差异必须按实际后端实现，不给用户展示与当前插件无关的进程或脚本选项。

| 项目 | P2-A Shell | P2-B 独立进程 |
| --- | --- | --- |
| 包与预览 | 同时读取 gpui-shell.json / conduit-plugin.json；不执行 JS | 读取 plugin.json；不启动程序 |
| 授权 | 系统能力请求、批准的 Policy 与宿主业务 API；首版关闭 Shell 持久存储和系统访问 | 本地程序信任与宿主 API 权限；后者不限制程序本身的 OS 能力 |
| 激活 | 首次显式操作才求值脚本、初始化和挂载视图 | 首次显式操作才启动进程并握手 |
| 停止 | 撤销视图、命令、Policy 任务与 HostModule 引用，等待宿主写入 | 取消请求、退出并确认整个子进程树，等待宿主写入 |
| 数据接口 | Conduit HostModule 使用下文相同的 namespace / CAS 语义 | JSON-RPC 使用下文方法和错误码 |
| 诊断 | 脚本 / 物化 / HostModule 时间、受限资源、宿主内存和脚本异常 | 进程状态、消息队列、stderr、子进程资源 |
| 开发资料 | JS 示例、生成类型、精确 Shell rev 兼容和宿主 API | Rust 示例、JSON-RPC 协议及可执行包 |

Shell 的 localStorage 不作为第二个数据源，数据位置和回退始终由本阶段注册表决定。Shell manager 默认路径不能直接代替 data-generation；公开加载与清理接口须先通过[复用评估](gpui-shell-reuse-assessment.md)的 G2 / G6。

## 目标与产品范围

交付“应用插件”设置页、本地目录安装、信任与授权展示、启用 / 停用、手动版本替换、上一版本回退、卸载、布局与插件数据保存、诊断和开发文档。插件启用范围为当前用户的 Conduit，全局启停；插件数据可以按工作区分区，首版不增加“仅在某工作区启用”的另一套授权状态。

首版不提供远程市场、自动下载或自动更新插件、不把发布者字符串当作已认证身份、不兼容 VS Code 扩展。用户只能明确选择一个本地包目录。将来引入签名或来源认证时再定义信任继承，当前每个新包摘要都需要用户明确接受。

首版清单中的权限均视为插件所需权限：接受安装时记录该包的完整授权，选择仅安装仍保持未启用；不接受则取消安装。初版不提供部分授权运行和运行时权限弹窗。撤销使用授权通过停用或卸载完成，包内容或权限变化必须重新接受。

## 设置页与用户操作

[settings/navigation.rs](../../src/app/settings/navigation.rs) 当前使用固定页编号及 `PAGE_ORDER`。在保留已有编号和 Skills / MCP 路由的前提下追加“工作台 / 应用插件”页，并纳入设置搜索。实现时按当前页面数量分配新编号，不在这个阶段顺带重写全部设置导航。

| 界面 | 必要内容 | 操作语义 |
| --- | --- | --- |
| 插件列表 | 名称、ID、版本、来源目录摘要、启用状态、运行状态、错误 | 搜索、安装本地目录、查看详情；区分“启用但未运行”和“正在运行” |
| 插件详情 | 三处贡献、请求的宿主权限、信任的包版本、最近诊断 | 启停、打开入口、重试、查看日志、替换版本、恢复上一版本、卸载 |
| 安装预览 | 来自已复制快照的清单、版本、大小、贡献和权限 | “安装并启用”或“仅安装”；选择取消则不建立信任记录 |
| 升级预览 | 当前 / 候选版本，权限增减，包来源和可回退状态 | 明确接受新包及对应运行方式的权限；不因发布者同名自动继承信任 |
| 布局偏好 | 活动项 / 状态项隐藏与顺序，恢复默认布局 | 用户选择优先于插件默认排序；宿主保留入口不能被插件隐藏 |

信任说明按后端提供。进程插件说明“该插件会作为本地程序运行，可以访问当前用户可访问的系统资源；下方权限只控制 Conduit 提供的数据与操作”。Shell 插件说明“该插件的脚本在应用内运行，可使用已批准的宿主接口；脚本运行可能影响应用响应”。不得把 Shell 描述为独立进程隔离，也不把进程插件的 JSON 权限描述为系统沙箱。

“启用”表示允许静态贡献注册和后续按需激活，不立即执行外部代码。管理页的“打开入口”属于显式用户动作。应用重启恢复到插件视图时先显示静态待加载占位，由用户点击加载；不能仅因上次选中过某视图就绕过首版的懒激活约定。

宿主 `writable = false` 时仍可查看管理信息，安装、授权、启停持久化及外部激活不可用；现有核心原生视图继续工作。界面说明当前操作不可用的实际原因。关闭 / 更新 / 同插件操作进行中时，阻止冲突操作。

## 数据目录与唯一状态来源

从 [store.rs](../../src/store.rs) 的 `Store::path().parent()` 推导插件根目录，继承 `CONDUIT_DATA_DIR` 和测试目录隔离。不得另行硬编码用户目录。

```text
<data-root>/
  state.json
  plugins/
    registry.json
    packages/<plugin-id>/<version>/<package-digest>/
      <所选后端的清单与代码文件>
    staging/<operation-id>/
    data/<plugin-id>/<data-generation>/
      global.json
      workspaces/<workspace-key-hash>.json
    logs/<plugin-id>/
    temporary/<plugin-id>/<runtime-generation>/
```

`registry.json` 保存安装、启用、当前包 / 数据代次指针、信任与授予的权限、上一版本及未完成操作。`UiSettings.plugin_layout` 只保存显示偏好，不能再保存一份插件启用或授权状态。高频视图内容、进程 / VM 对象、请求和日志不写入聊天 Store。

包内文件按后端区分：P2-A 是 gpui-shell.json、conduit-plugin.json 与 JS 文件；P2-B 是 plugin.json 与 bin。下面给出 P2-B 的注册记录示例；摘要是格式占位值，不对应真实包。

```json
{
  "schemaVersion": 1,
  "revision": "1",
  "plugins": {
    "example.workspace-overview": {
      "installed": true,
      "retainedData": null,
      "desiredEnabled": false,
      "active": {
        "backend": "process",
        "runtimeRevision": null,
        "version": "0.1.0",
        "packageDigest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
        "dataGeneration": "data-1"
      },
      "trustedPackages": {
        "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa": {
          "permissions": ["workspace.metadata.read", "session.summary.read"],
          "shellCapabilities": null,
          "acceptedAt": "2026-11-04T00:00:00Z"
        }
      },
      "previous": null,
      "pendingOperation": null
    }
  }
}
```

Shell 记录使用 `backend = "shell"`，`runtimeRevision` 保存已验收的 Shell 提交，信任记录的 `shellCapabilities` 保存宿主规范化后的已批准系统能力（首版为明确关闭系统访问和持久存储的集合），不能只记宿主业务权限。两份清单、该摘要及对应授权必须一致，加载时不重新盲信 manifest 请求。运行时升级超出已验收兼容范围时保持静态未激活，重新验证后才允许执行。进程记录的这两个 Shell 字段为 null；首版只接受已选定后端的包。

运行中的 generation 与数据目录的 data-generation 是不同身份：前者每次启动变化，后者在版本升级 / 回退事务中切换。进程崩溃或脚本实例失败不会自行创建一份新的持久化数据。宿主从注册表解析数据代次，插件不能在 API 参数中选择任意目录或数据代次。

所有安装事务由一个后台注册表写入器串行处理，带单调 revision；落盘采用同目录临时文件、刷新和原子替换，并返回明确确认。借鉴 [store.rs](../../src/store.rs) / [persistence.rs](../../src/persistence.rs) 的方式，但安装操作不可像可替代 UI 偏好一样被任意合并丢弃。

注册表损坏或 schema 不受支持时，保留原文件，停用外部加载并在管理页显示恢复入口；不把损坏当成空列表覆盖，也不影响聊天历史的正常读取。较旧应用发现更高 schema 时同样只读保留。回退到不支持插件的旧版本应用可能丢失其不理解的布局字段，但插件注册与数据目录仍应独立保留。

## 包复制、摘要与安装事务

v1 接受目录包，拒绝符号链接、junction 和其他重解析点，不解压未知归档格式。包路径、ID、版本和文件名先校验，再进入宿主管理目录；拒绝设备名、备用数据流、父路径、绝对路径和按目标 Windows 文件系统语义冲突的名称。

包摘要以实际复制出的文件计算：规范化包内相对路径分隔符，按路径排序，逐项输入长度前缀、路径字节、文件长度及文件内容到 SHA-256。清单包含在摘要中，摘要本身存于外部注册表。明确文件列表和长度编码，避免不同文件边界产生相同拼接输入。路径和内容均从同一份快照读取，不能信任源目录报告的摘要。

| 安装步骤 | 状态变更与失败行为 |
| --- | --- |
| 1. 读取与复制 | 后台复制到 staging，限制大小与数量，重解析清单并重新校验；失败删除本次临时结果，源目录不变 |
| 2. 冲突与预览 | 检查注册 ID、版本、贡献和宿主 API；相同 ID / 版本 / 摘要视为已安装，相同版本不同摘要要求作者更新版本 |
| 3. 用户接受 | 预览当前快照的权限及信任说明，明确选择安装操作；取消不登记授权 |
| 4. 发布包 | 将快照移入以摘要命名的包目录；目标存在时先验证后复用，不直接覆盖 |
| 5. 提交注册 | 原子写入 active 指针、授权和 desiredEnabled；只有确认成功后才注册贡献 |
| 6. 按需启动 | 首次用户动作启动前后台复核包摘要；变更导致授权失效，管理页提示重新安装 |

指针提交前崩溃留下的包只作为未引用内容，不能被启动扫描自动注册。摘要检测包内容是否变化，不证明发布者身份，也不构成对恶意本地程序的系统级隔离。删除 staging 或旧包前必须解析实际路径，并验证它位于宿主管理根目录内。

P2 的开发快照沿用上述路径与摘要规则，但不写入 durable trust / desiredEnabled；应用重启后无开发参数就不加载。开发快照也不能绕过宿主可写检查或修改普通安装记录。

## 启停、升级、回退与卸载

| 操作 | 必须保证的行为 |
| --- | --- |
| 启用 | 当前包兼容且已接受该摘要与权限；先持久化 desiredEnabled，再注册静态贡献；未被打开时不启动 |
| 停用 | 立即拒绝新命令 / 激活并发起 P2 停止；写入 desiredEnabled=false；撤销贡献、订阅和用户动作令牌，清理完成后标为已停用 |
| 停用保存失败 | 本次运行继续禁止插件，明确显示“本次已停用，偏好未保存”；不能声称重启后也已停用，保留重试保存入口 |
| 手动重试 | 原代次清理完成后才创建新代次；不重放上一条可能有副作用的用户命令 |
| 卸载 | 先停用并等待退出，再移除注册；默认保留插件数据，用户可明确选择同时删除数据；仅删除宿主管理范围内且无引用的包 |
| 存储或磁盘错误 | 不显示已成功；保留最后确认的注册状态，并记录可重试的操作 |

升级采用包与数据代次成对切换，减少包版本回退与数据格式不匹配的问题。

1. 候选包经过与安装相同的复制、摘要、兼容和信任步骤；记录 `pendingOperation`，当前 active 指针仍指向旧版本。
2. 拒绝该插件的新操作，停止旧运行实例并等待其数据写入确认。未确认退出时不替换包、不复制可能仍在变化的数据。
3. 将旧数据代次复制到新的数据代次，准备并完整校验候选贡献集合、清单与宿主能力；此时不执行候选代码。
4. 校验通过后，原子提交新的包指针与数据代次，并把原 active 记为 previous；确认成功后按 desiredEnabled 注册候选静态贡献，保持未运行。此前失败则保留旧 active，可恢复旧静态入口。
5. 用户下一次显式打开入口才触发候选初始化与激活。初始化或运行失败进入普通 Failed 状态，由用户决定重试或回退；不能自动重复运行旧命令。

包目录、数据代次均为准备好的独立目录，关键切换集中在注册表的一次原子替换。第一阶段的批量注册在提交前进行完整预校验；若内存注册仍意外失败，保持外部实例停用并显示诊断，不让不完整贡献继续使用。启动恢复时只按已提交 active 加载；未提交候选不得在恢复过程中执行。`pendingOperation` 清理必须幂等，使用同一 operation-id 不重复复制或启动。

“恢复上一版本”原子切回 previous 的包和数据代次，并停止当前代次。界面必须说明会恢复到升级前的插件数据，当前版本新增的插件数据不会出现在恢复后的视图中。保留被替换的数据目录直到清理策略明确处理，不影响工作区文件或聊天历史。此策略只覆盖宿主管理的数据，不能撤销原生程序直接对系统执行的操作，或以后扩展授权后产生的外部副作用。

首版最多保留一个 previous 包 / 数据代次；再次升级前先检查空间并按保留规则处理更旧代次。跨插件没有依赖安装或事务，插件不能要求静默启用另一个插件。

卸载但保留数据时，注册表保留一个不参与加载的记录：installed=false、desiredEnabled=false、active / previous 为空，retainedData 指向最后的数据代次，清除信任与授权。管理页可以筛选这些保留数据；再次安装同 ID 时由用户选择复用或新建，仍需重新接受当前包。选择删除数据后再移除该记录。包清理失败时显示“已卸载，文件清理待重试”，不能重新注册入口。

## 插件数据 API 与布局恢复

P3 声明并实现 `storage.read`、`storage.write` 能力。读取需 read，写入需 write；没有对应授权时返回 PermissionDenied。下表是逻辑方法：P2-B 通过原有 JSON-RPC 调用，P2-A 通过 Conduit HostModule 的有界异步调用提供相同数据语义。两者共用存储实现与写入确认，不并行保存 Shell localStorage。

| 方法 | 参数与结果 | 约束 |
| --- | --- | --- |
| `storage/get` | scope、key、contextVersion → value、revision | scope 为 global 或 workspace；workspace 只对应当前授权上下文 |
| `storage/set` | scope、key、value、expectedRevision、contextVersion → revision | 按 namespace 文件做比较并交换；数据成功持久化后回复 |
| `storage/delete` | scope、key、expectedRevision、contextVersion → revision | 删除指定键；不接受文件路径或通配符 |

使用 RevisionConflict 表示 expectedRevision 已过期；P2-B 对应预留的 JSON-RPC 错误码 `-32008`，P2-A 使用宿主模块的结构化错误约定，不包装成 RPC 消息。revision 对整个 namespace 生效，不只针对单键；首次为空的 namespace 使用 revision `"0"`。SDK 在冲突后重读并由业务决定合并，不能自动覆盖新值。accepted 写入一旦开始提交，contextVersion 改变不会撤销已受理的数据；结果可被 UI 丢弃，但写入目标仍绑定受理时的工作区及数据代次。

数据以宿主 envelope 保存 schemaVersion、revision 和 values；插件可在自己的键中记录业务数据版本。业务迁移仅修改当前数据代次，上一版本的数据代次保留用于回退。v1 不提供任意文件存储、密钥库或事务脚本接口。

布局偏好保存在 `UiSettings.plugin_layout`，包括活动项与状态项隐藏 / 顺序、最后选择的 navigation / right ViewId、右侧宽度及折叠状态。插件视图轻量选择与滚动可由宿主保存有限条目，必须按稳定 ViewInstanceKey 恢复；缺失插件、隐藏项、作用域不匹配或非法宽度按 P1 回退 / 限宽规则处理。

新增布局字段采用 `serde(default)`，旧 state.json 可直接读取；不增加聊天记录中的插件数据字段。保存布局沿用现有异步持久化，不因状态项每次刷新写盘。恢复只影响显示状态，不恢复在途命令、授权弹窗或运行实例。

## 安装与存储预算

运行时限额以所选 P2 为准；模板和管道限额仅用于 P2-B，不能替代 P2-A 的脚本执行与内存限额。以下为本阶段初始设计值，实际发布前按包与性能样本验证。

| 项目 | 初始值 / 行为 |
| --- | --- |
| 注册数量 | 最多 64 个插件记录，含保留数据记录；超过后要求用户卸载或清理不需要的数据 |
| 单个包 | 最多 128 MiB、2048 个普通文件；每份清单受所选 P2 的 256 KiB 上限约束 |
| 包复核 | 后台执行，可取消，最多 30 秒；超时保持未激活并提供重试 |
| 注册表 | 最多 1 MiB；原子写入前校验完整结构和 revision |
| 数据 key / value | key 为 1–64 个 ASCII 字母、数字、点、下划线或连字符；单 value 最多 64 KiB JSON |
| namespace | 最多 128 个键；路径由宿主生成，key 不参与文件路径拼接 |
| 数据代次 | 每插件每个数据代次最多 10 MiB，含全部工作区；默认最多保留当前与上一代次 |
| 写入 | 每插件串行队列最多 32 项；超限返回 ResourceLimit，不阻塞 UI |
| 宿主结构化日志 | 每插件最多 2 个 1 MiB 滚动文件，默认只记录协议与生命周期元数据 |
| 原始输出 | 每插件内存环形缓冲最多 64 KiB；P2-B 为 stderr，P2-A 为可归属插件的脚本日志；默认不持久化 |

拷贝升级数据前计入候选目录所需空间，不能只计算当前 active。空间不足时保留旧版本并明确失败。删除数据前验证完整目标路径处于管理根目录，拒绝重解析点和来源不明的目录，不基于插件提供的任意路径递归操作。

## 诊断、退出与安全降级

管理页展示激活耗时、实例状态、超额 / 超时计数及最近错误。P2-B 增加进程、消息和队列指标；P2-A 增加脚本 / 原生物化 / HostModule 耗时与资源指标，不把共享宿主 RSS 冒充单插件内存。结构化日志使用允许字段列表，避免记录完整消息体、环境变量、会话内容和路径。原始 stderr 或脚本日志可能含敏感信息，不能保证自动识别全部内容；导出前由用户预览选择，不自动上传。

P2-B 的消息限额约束宿主排队与绘制负载，不限制原生程序自身 CPU / 内存；该后端测量进程资源并提供停止入口，Windows Job 强制配额另行评估。P2-A 的堆与执行预算必须在前置验证中落实；当前锁定 Shell 无默认堆上限且看门狗为秒级，不能省略该项验收。两个后端均不因本阶段完成而获得操作系统沙箱保证。

所有注册表 / 数据写入确认接入 P2 的退出屏障。应用更新前先冻结新插件工作，再停止全部外部运行实例、完成写入并确认包文件不被占用；更新失败恢复原应用时保持插件静态 Registered，等待下一次显式操作。插件 StopFailed 或未确认的关键写入错误应阻止安装交接，并说明具体阻塞项。

恢复默认布局只调整显示偏好，不改变信任、启用或插件数据。卸载一个插件不影响其他插件；注册表读取失败时降级为仅核心功能，插件加载失败不阻止应用主窗口出现。
