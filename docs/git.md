# Git 工作流

Git 查询、命令执行和 Diff 读取在后台完成。界面使用左侧变更/分支导航和主区标签；各工作区保留提交草稿、快照与打开的 Diff。操作前再次检查仓库、引用及工作区身份，迟到结果不能覆盖当前工作区。

## 变更与提交范围

变更侧栏由工具栏、独立滚动文件列表和固定提交区组成。默认按 Changes / Unversioned Files 分组，可切换状态分组；支持单文件、整组、全选及批量暂存/移出暂存。暂存状态按整文件显示为已暂存或未暂存，保留变更类型和重命名信息，双击打开 Diff。暂存后再次修改的文件先显示未暂存，自动暂存完成后显示已暂存；提交和 AI 说明生成仅接受全部改动均已暂存的文件。

**勾选控制提交范围，提交只包含勾选文件的已暂存内容。** 自动暂存更新当前索引中已跟踪文件的修改和删除，包括已手动暂存但尚未提交的新文件；首次提交前同样适用。全新、尚未暂存的文件必须手动加入，遵守 `.gitignore`、嵌套 `.gitignore`、`.git/info/exclude` 和全局 `core.excludesFile` 排除规则，不强制加入被排除的文件。`git add -N` 只记录添加意图，没有实际暂存内容，仍需手动暂存。已跟踪文件后来匹配排除规则，仍按 Git 的跟踪语义更新。新文件移出暂存后恢复为未跟踪文件，不会自动重新加入。不希望提交某文件时取消勾选；主动移出的已版本化修改可能在下次常规刷新重新暂存。

只读、关闭中、Git 写操作、AI 说明生成、同仓库 CLI 任务、未结束的 merge/rebase 或冲突会阻止自动暂存。刷新期间遇到任务占用时保留自动暂存请求，恢复空闲后继续。操作后的结果刷新只读状态，避免自动重试循环。提交前再次检查勾选文件是否有未暂存改动，避免提交旧的暂存内容。

提交区提供 Commit / Commit and Push、可选 Tag 和 AI 说明生成/取消。AI 配置可跟随当前会话或使用独立引擎/服务/模型，生成范围与文件选择一致。执行期间按钮显示加载状态并阻止重复提交；长说明和窄窗不能遮挡底部操作。

## Diff、分支与日志

Diff 是按工作区与路径去重的只读标签，提供已暂存/未暂存内容，支持首次提交、删除和重命名。已暂存文件默认查看暂存快照，未暂存文件默认查看全部改动。外部变化与刷新必须保留正确的版本来源，不能用工作区完整文本冒充待提交快照。

分支树展示本地、远程和标签，支持搜索、收藏与滚动；默认展开 Local，搜索临时展开匹配分组。日志与提交文件列表使用虚拟化，加载提交详情时显示占位，刷新已有日志时保留内容。

分支菜单提供创建、重命名、删除、切换、跟踪、推送、更新以及 merge/rebase 与冲突恢复。linked worktree 占用、陈旧引用、脏工作区和未结束操作必须在执行前校验。菜单点击需覆盖 mouse-down → 重绘 → mouse-up，不能仅用 Enter 测试替代鼠标路径。

打开分支列表和普通刷新不自动 fetch。仓库状态与分支探测保留各自的可见性/周期调度，已有查询或写操作时不叠加周期请求。

## 冲突解决

交互参考 JetBrains 官方《Resolve Git conflicts》（`https://www.jetbrains.com/help/idea/resolve-conflicts.html`，2026-08-17）：冲突文件列表、整文件采用某侧、以共同祖先为初始结果的三栏合并、逐块接受/忽略、批量应用无冲突变更，以及保存后继续 Git 操作。

检测到新冲突时直接打开首个文件的三栏合并编辑器；已有其他弹窗时保留 Git 侧栏入口。普通刷新不会反复弹出同一批冲突。外部终端、stash 等产生的 unmerged 文件同样列出，不要求存在 `MERGE_HEAD`。冲突文件单独分组，不能通过普通暂存/移出暂存按钮绕过解决流程。

- 单文件直接展示合并编辑器；多文件在左侧列表切换，窄窗口将列表放到编辑器上方。当前/传入版本标题下可采用该侧完整文件，会写入工作区并暂存；某侧不存在时代表删除。
- 左侧读取 index stage 2，右侧读取 stage 3，共同祖先读取 stage 1。普通冲突的中间结果按块编辑；若磁盘内容已不同于自动合并结果，则完整保留到中间栏作为手工草稿，并提示审阅，批量应用不会覆盖这些编辑。两侧只读可复制；版本栏显示分支/提交标识。Rebase 会明确提示 Ours 为变基目标、Theirs 为重放提交。
- 相对共同祖先计算变更块，三栏共享外层滚动和块对齐；块内长内容可独立滚动。交界处箭头应用或撤销某侧，叉号忽略或撤销忽略。两侧均应用时按左、右顺序保留；相同内容只保留一次。
- “应用无冲突变更”只处理未决定且不重叠的变更，不自动解决真正冲突。手动编辑的块不会被批量操作覆盖，需点击“标记此块已解决”。支持前后变更导航、折叠未变更内容、编辑器搜索、语法高亮和块重置。
- 未处理的块会阻止保存。“保存并标记解决”写入结果并暂存，自动打开下一个冲突文件；全部解决后由已有“继续”完成 merge/rebase。关闭或 Esc 不保存文件，草稿按工作区保留在当前应用进程；重新加载会丢弃该文件草稿。

保存在原有 Git 写操作互斥内运行，重新核对仓库根目录、HEAD、操作来源、索引三个阶段和工作文件指纹。使用普通 `index.lock` 与临时索引，保留其他暂存文件；暂存失败时仅在文件未被再次修改的情况下恢复原文件。二进制/非 UTF-8 文件支持整文件选择，使用 Git checkout 保留字节与转换规则；整文件采用保留所选版本的执行权限位，文本合并按共同祖先和双方版本合并执行权限；新增文件的权限分歧须明确采用某侧或在外部解决。文本读写由 Git 按文件属性处理工作区编码、换行符和 clean/smudge 转换，转换失败保留原文件与冲突索引。保存拒绝残留的冲突边界标记并支持自定义标记长度，普通等号分隔线（如 Markdown 标题）不视为冲突。

当前边界：文本版本上限 2 MiB、30,000 行和 400 个对齐块；超过限制可选择完整版本。符号链接、目录联接、子模块交由外部工具处理。中间编辑器按变更块组织，尚不提供跨块统一撤销、字符级简单冲突合并、保存后的“撤销解决”、列表多选批量采用、列宽拖动或跨进程草稿恢复。

## 版本标签

标签是 Git ref，生成候选不会修改 `Cargo.toml`、源码或自动提交。稳定标签按 SemVer 排序；“生成下一个”以本地最高的有效 `vMAJOR.MINOR.PATCH` 为基准，支持 Major / Minor / Patch 和 1–100 步长，递增后将右侧段归零，跳过已占用名称。没有有效版本时从 `v0.1.0` 起步。

- Commit 将可选轻量标签明确指向本次新提交的对象 ID。
- Commit and Push 仅原子推送当前分支与本次标签，不用 `--tags`、不 force；远端不支持原子推送时报告失败，不隐式拆成两次推送。
- 发布型标签必须符合目标仓库规则。本仓库要求稳定 `vX.Y.Z` 与 Cargo 版本一致，Actions 仍是最终校验方。
- 标签选择器显式刷新时使用 `git ls-remote --refs --tags` 查询当前上游，区分仅本地、仅远程、两端存在和未查询；不 fetch、不写本地 refs。失败保留上次成功快照。
- 提交和标签已创建但推送失败时保留本地成果。先核对远端状态并推送分支，再使用标签重试；重试重新核对 HEAD、标签目标、上游和推送地址，远端分支包含该提交后才推标签。
- 远端同名标签指向相同提交视为成功，指向其他提交则拒绝。重试状态仅保留在当前应用进程，不支持多个 push URL。

远程标签删除/移动、强推和自动清理旧标签不在此工作流内。发布操作见[发布与更新](releasing.md)。

## 并发与通知

Git 写操作按共享仓库与 CLI 任务互斥，覆盖 linked worktree；不同仓库的聊天不应被阻塞。不可操作原因保留在按钮提示，必要的重试入口随对应状态提供。

操作结果和校验错误统一进入[通知中心](notifications.md)，即使 Git 面板已经打开也显示统一 Toast；普通进度只进入历史，避免自动暂存频繁打扰。提交区和分支面板底部不再重复显示消息，标签推送重试按钮仍按需保留。通知绑定原工作区，后台操作完成不能错误跳往当前工作区。

## Diff 审查意见

工作区 Diff、分支比较和提交 Diff 的行旁提供评论入口。选择同一侧的连续代码行后，添加并保存意见；评论记录文件、比较范围、原始片段和补丁指纹。状态可设为待处理、待复核、已解决或不采纳。源码变化后保留原始证据，显示位置需要复核，不自动移动意见或判定已解决。

“标记已查看”仅对当前文件的补丁版本有效。它不执行暂存、提交或代码写入。

勾选意见后可附到同一工作区内的现有会话或新会话。内容追加到目标草稿，保留原会话草稿；由用户点击发送后才调用引擎。“准备 AI 审查”提供启用引擎的选择，建立只读审查会话草稿，附带当前文件补丁、来源、指纹、覆盖说明和结构化 JSON 格式。保存请求标识和原补丁，只绑定这次新建的审查会话；不宣称已捕获其他文件的一致快照。

审查会话的普通消息成功完成后，读取本轮最后一条助手回复。仅接受完整 JSON 对象或单个完整 JSON 代码块；核对请求标识、补丁指纹、精确文件路径、左右侧及原补丁实际包含的连续行，再整批导入。每条发现保留 AI 来源、优先级、标题、原始代码片段和来源会话，初始状态为“待复核”，由用户决定处理。任何一条无效则整批不导入；取消、失败、工具输出和原生命令结果不会导入。原始回复保留在会话里，可在同一审查会话中要求修正后重试。成功导入后不再重复导入该报告，不会重开已解决意见。空发现列表单独显示，不代表审查通过，不改变文件“已查看”状态。

会话工具栏的“工作区审查意见”可查看该工作区全部已保存的意见，包括已提交、删除或重命名前的文件。此入口展示历史证据，未重新核对当前源码；附到当前会话前仍须由用户检查。评论保存在应用状态中，异步保存失败时显示错误，保留内存中的意见以待重试。

该收件箱也展示 AI 审查报告状态及失败原因，可打开原审查会话。当前回复结束后可以移除报告记录，释放捕获的补丁并停止后续导入，已保存的意见和会话仍保留。已删除或归档的来源会话不会错误地跳转到同 ID 的其他会话。报告最多 50 条、补丁总计 4 MiB；单次草稿与回复各最多 128 KiB，每份报告最多 100 条发现。导入采用同样的评论总量和片段限制。旧版本保存的人工评论仍可读取。尚不自动修复代码或发布到 PR。

GitHub PR 面板的“同步讨论到审查收件箱”可以保存远端行级和文件级讨论。远端当前/原始位置、原提交与 Diff、已解决/过期状态和本地处理状态分别保存；刷新后再次同步按稳定讨论 ID 更新。本地状态不被远端变化覆盖，变化会另作复核提示。远端讨论不直接附着到本地 Diff，也不改变本地已查看状态。详见[项目工具的 PR 审查同步](project-tools.md#pr-审查同步)。

每条评论最多 8 KiB，代码范围最多 200 行和 32 KiB，单次附加内容最多 128 KiB。评论总量上限 1000 条，文件已查看记录最多 2000 条。列表分批展开。未保存的评论编辑草稿仅属于当前 Diff 视图，关闭视图前应先保存。
