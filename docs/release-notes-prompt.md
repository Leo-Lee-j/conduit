# AI 发布时生成更新说明

本提示词供正在处理 Conduit 发布任务的 AI 使用。AI 在本地生成并提交版本说明，
GitHub Actions 只校验和读取该文件，再用于 Release 和签名更新清单。

## 可直接使用的提示词

> 为 Conduit 本次发布生成 `release-notes/vX.Y.Z.md`。从目标 Cargo 版本、上一个
> 已发布版本和本次实际发布的代码变更出发，使用 `release-notes/TEMPLATE.md`
> 的结构撰写中文更新说明。先给出一句话概述，再列出最多 5 条更新亮点，最后按
> 新增、改进、修复及必要的升级提示组织详情。每条说明具体功能或操作发生了什么
> 变化，对用户有什么帮助；合并相关提交，省略纯重构、测试、构建及维护记录。
> 不编造功能、性能数字或测试结论，不把 commit 标题和哈希直接作为更新说明。
> 保留已有的人工文案，移除空分类和模板占位符。生成后校验文件，并确保文件包含
> 在将被打标签的发布提交中；不要自行扩大用户授权的发布范围。

## 确定变更范围

1. 根据用户指定版本和 `Cargo.toml` 确定目标 `vX.Y.Z`；真正发布前同时更新
   `Cargo.lock` 中的应用版本。不要为普通功能开发任务提前创建版本说明或标签。
2. 查询已经发布的稳定版本，例如
   `gh release list --exclude-drafts --exclude-pre-releases --limit 100 --json tagName,publishedAt`。
   选择小于目标版本、且属于本次发布历史的最近已发布版本作为基线。
   不把失败构建遗留的标签或 draft 当成已发布版本。
3. 若已存在目标标签，查看基线到该标签的提交和 diff；若在准备新标签，查看基线
   到 HEAD 的提交，以及准备纳入本次发布的未提交变更。不要把无关并行修改写进说明。
   例如使用 `git log --no-merges --format='%s%n%b' vBASE..HEAD`、
   `git diff --stat vBASE..HEAD`，再查看与用户行为有关的实际修改。
   有 CodeGraph 索引时，代码理解遵循根目录 `AGENTS.md` 的检索规则。
4. 无已发布版本时，根据实际可用功能撰写首版简介。无法核实发布基线时，先用已有
   证据整理草稿，在发布前解决范围问题，不猜测哪些版本已发布。
5. 存在同版本未发布说明时，在保留人工编辑的基础上补充；再次核对最终发布内容。
   不改写已发布版本，也不要仅凭模糊的提交标题推断用户功能已经完成。

## 文案与格式

- UTF-8 Markdown，文件名为 `vX.Y.Z.md`，首行严格为 `# Conduit vX.Y.Z`。
- 标题下用一句话概括本次更新，使用自然、具体的中文。
- `## 更新亮点` 必须保留，列出 1～5 条最值得关注的变化；变化少时不要凑数。
- `## 新增`、`## 改进`、`## 修复` 只保留有内容的分类。同一改动在详情中合并成一条；
  亮点可以是详情的简短概括，不需要逐条重复。
- `## 升级提示` 只用于确有必要的配置迁移、兼容性变化或用户操作；没有则删除。
- 不显示 commit 哈希、PR 编号、内部文件路径、测试日志或 AI 生成过程。
  若构建或基础设施修改确实改变用户安装、更新或使用行为，可以描述它的用户影响。
- 示例：将 `fix(updater): preserve composer draft on restart` 改写为
  “修复更新重启后输入草稿丢失的问题”。避免“若干优化”“全面提升体验”等空泛表述。
- 可以在末尾添加指向官方仓库对应版本 compare 或 release 的“查看完整变更”链接。
  文件中使用完整 URL，避免客户端无法解析的仓库相对链接。
- 删除所有 `{{...}}` 占位符和模板注释；正文不包含空分类或未完成事项。

## 发布前完成

```powershell
./scripts/prepare-release-notes.ps1 -Tag vX.Y.Z
git diff --check
```

第一条命令只校验文件，不生成文案、不调用模型、不发布版本；可从任意工作目录运行。
发布前再执行[发布文档](releasing.md#发布)中的代码验证，并将说明文件放入发布提交。
CI 读取标签提交里的文件；缺失或格式不正确时会停止，不回退到原始提交历史。
