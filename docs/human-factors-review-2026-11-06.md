### HFE-01 · 普通退出丢弃输入草稿

**场景与影响：** 用户编写较长任务，切换会话后暂存草稿，或编辑提交说明，随后关闭应用。普通退出后这些输入不恢复；更新重启却能恢复。相同的“离开并重新打开”产生不同结果，容易造成返工。

**证据：** [app.rs:538](../src/app.rs#L538) 的关闭路径保存 Store 并清理任务，没有保存编辑草稿；[app.rs:777](../src/app.rs#L777) 只把排队消息复制进 Store；[store.rs:252](../src/store.rs#L252) 不包含普通聊天、工作区或提交说明草稿。[update.rs:322](../src/app/update.rs#L322) 另有更新专用恢复快照。[使用指南:111](usage.md#L111) 已明确说明这个限制。因此这是现有产品策略的体验缺口，不是新出现的保存回归。

**建议：** 将聊天、工作区、提交说明及附件引用纳入统一的本地草稿恢复机制，按上下文保存并在启动时恢复。恢复草稿保持未发送状态；保存失败时保留窗口与输入，并提供重试。若暂不支持持久草稿，至少在存在未发送内容时说明退出后果并允许返回编辑；无草稿时直接退出。

**验收：** 同时准备两个会话草稿、一个未创建会话的工作区草稿、一条排队消息和一份 Git 提交说明；正常退出再打开后分别恢复到原上下文，排队消息保持暂停，附件可用且不自动发送。保存故障不能无提示关闭窗口。更新恢复路径继续成立。

### HFE-02 · 关键停止操作缺少键盘与按钮语义

**场景与影响：** 用户用键盘发送任务后，希望立即停止。运行中的圆形停止控件由普通布局元素实现，没有控件自己的焦点、名称或按键激活路径，现有全局快捷键也没有停止动作。普通发送可以用 Enter，停止缺少相同等级的操作入口。

**证据：** [composer.rs:682](../src/app/composer.rs#L682) 的停止控件和 [composer.rs:716](../src/app/composer.rs#L716) 的发送控件均为 `h_flex` 加点击处理；停止图形只是内部小方块。[app.rs:296](../src/app.rs#L296) 的绑定表没有取消当前任务的快捷键。这里确认的是源码缺少语义与键盘实现，Narrator 的实际输出仍需 V-03 验证。

**建议：** 使用共享 Button 实现发送/停止，提供可访问名称、焦点可见态、禁用/停止中状态和明确提示。新增“停止当前会话”的命令入口与可发现快捷键，动作仍绑定当前会话。保留现有队列暂停和进程树清理语义；停止过程完成前不要把界面表现为已空闲。

**验收：** 只用键盘完成发送、聚焦停止、激活停止与返回编辑；读屏能区分发送、停止和停止中。后台其他会话继续运行；停止后队列保持暂停。中文候选确认和弹窗 Esc 不误触停止。

### HFE-03 · 审批决策信息默认折叠

**场景与影响：** 聊天中出现“请求执行命令”与“允许本次”，但命令、路径等信息需要再展开 JSON 才能看到。高频审批时，界面容易促使用户按通用标题作决定。

**证据：** [protocol.rs:795](../src/protocol.rs#L795) 生成通用审批标题，Claude 路径也主要显示工具名；[state.rs:296](../src/app/state.rs#L296) 默认没有展开项。[shell.rs:503](../src/app/shell.rs#L503) 显示标题和通用说明，[shell.rs:555](../src/app/shell.rs#L555) 仅展开时显示 `approval.detail`。通知中心已有提取命令与路径的 [approval_message](../src/app/notifications/approvals.rs#L14)，可复用其解析思路。

**建议：** 审批卡默认显示工作区/会话、操作类别、命令或受影响路径，以及授权范围；长内容明确截断并提供完整查看。协议原文继续作为次级详情。复用一套结构化摘要，同时保留通知已有的请求绑定和失效检查。

**验收：** 命令、文件修改、网络请求及不支持“允许本次”的情况，都能在首次出现时读出决定所需信息；完整命令可查看和复制。对话卡与通知表达同一操作；多审批时不会将上一项的信息套到下一项。用户问题仍使用回答表单。

### HFE-04 · 提交前缺少与暂存内容一致的 Diff

**场景与影响：** 同一文件先修改并暂存 A，再增加未暂存修改 B。用户在变更列表查看 Diff 会看到 A+B，但点击提交实际只提交 A。用户可能误以为 B 已包含在本次提交中。

**证据：** [git.rs:799](../src/git.rs#L799) 的文件 Diff 明确使用 `git diff HEAD`，包含暂存与未暂存内容；[git_diff.rs:269](../src/app/git_diff.rs#L269) 也正确标为“HEAD → 工作区（含暂存）”。[git_ui.rs:347](../src/app/git_ui.rs#L347) 与 [git_ui.rs:383](../src/app/git_ui.rs#L383) 则仅提交勾选的已暂存文件。当前没有伪造比较范围，但缺少从提交任务直接核对暂存版本的界面。

**建议：** 在同一 Diff 中显式区分“待提交（HEAD → 暂存区）”“未暂存（暂存区 → 工作区）”“全部工作区变更”。从提交区进入时默认核对待提交内容；保留原有总览。部分暂存文件同时显示两个状态，提交按钮附近常显本次文件数及范围。

**验收：** 构造 A 已暂存、B 未暂存、C 未勾选的场景；待提交预览只含 A，提交结果与该预览一致。切换模式时标题与内容同步。提交前分支/暂存区变化的现有校验继续有效。

### HFE-05 · 会话切换重置阅读位置

**场景与影响：** 用户在长对话 A 中查看一段旧代码，切到 B 处理审批后再返回 A，需要重新寻找原位置。多会话并行越频繁，找回上下文的成本越高。

**证据：** [sessions.rs:927](../src/app/sessions.rs#L927) 清空消息定位状态；[sessions.rs:945](../src/app/sessions.rs#L945) 重置时间线并将 `at_bottom` 设为 true。[shell.rs:197](../src/app/shell.rs#L197) 随后滚到末尾。现有“转到最新消息”按钮不能恢复此前阅读点。

**建议：** 按会话保存消息锚点、锚点内偏移和是否跟随末尾；普通切换恢复阅读点。首次进入、主动“转到最新”和通知指定定位分别处理，不覆盖用户手动阅读状态。使用稳定消息标识，避免虚拟列表增删或工具折叠导致索引漂移。

**验收：** A 在历史中部，B 持续输出；往返十次仍回到 A 的同一消息附近。字号变化、工具展开、正文重新加载后锚点可恢复；原本处于末尾的会话继续跟随新消息。

### HFE-06 · 侧栏自绘交互缺少完整键盘路径

**场景与影响：** 用户能通过搜索切换会话，但难以沿着当前侧栏完成展开、归档筛选、调用行菜单等操作。鼠标可点与键盘可达没有统一。

**证据：** [sidebar.rs:372](../src/app/sidebar.rs#L372) 的会话行使用布局元素与点击/右键处理；[sidebar.rs:557](../src/app/sidebar.rs#L557) 的“更多”、[sidebar.rs:624](../src/app/sidebar.rs#L624) 的归档筛选以及 [sidebar.rs:654](../src/app/sidebar.rs#L654) 的添加按钮没有对应的局部焦点/按键实现。Ctrl+E、Ctrl+P 是已有替代导航，但不覆盖这些行操作。[plugin_ui.rs:472](../src/app/plugin_ui.rs#L472) 还特意关闭工作区活动按钮的默认焦点环，替代提示需要核验。

**建议：** 普通动作用共享按钮；会话列表采用明确的列表/树键盘模式，区分焦点项与选中项。支持方向键移动、Enter 打开、菜单键或 Shift+F10 调用同一行菜单，并暴露展开、选中、归档及运行状态。虚拟化时保留逻辑焦点并滚动到可见位置。

**验收：** 不用鼠标完成选择工作区、展开会话、打开第 100 个会话、调用菜单、显示归档和收起导航。Tab 顺序不遍历所有离屏行，也不丢失当前焦点；菜单关闭后回到来源项。

| 暗色 focus / 输入框 surface | `#4b4b54` / `#19191c` | 2.03:1 |
| 亮色 focus / 输入框 surface | `#b4b4bd` / `#ffffff` | 2.06:1 |

计算方法：将每个 sRGB 通道归一化，按 `c <= 0.04045 ? c/12.92 : ((c+0.055)/1.055)^2.4` 线性化，求 `L = 0.2126R + 0.7152G + 0.0722B`，最后求 `(Lmax+0.05)/(Lmin+0.05)`。

**建议：** 正常可用的信息文字以 4.5:1 作为设计基准，禁用和装饰内容单独处理；不要用降低可读性代替信息层级。提高输入框聚焦边界的辨识度，并统一焦点提示。为界面文字提供独立于聊天正文的字号/密度策略。24px 图标不等于 24px 点击区域，触达尺寸另按 V-02 验收。

**验收：** 两套主题逐一核对实际背景上的功能文字；焦点状态在输入区、列表、弹窗和菜单中均明显可见。放大字体后标签和操作不被裁切。上述焦点比值只表示这条自绘边框的风险，不推断所有库组件焦点环都不合格。

### HFE-08 · 首次任务的引导和就绪状态不准确

**场景与影响：** 首次打开的主区域写着“连接一个本地工作区”，主要内容却是会话热力图；添加目录依赖侧栏小加号或工作区菜单。创建空会话后显示“已就绪”，用户可能把它理解为 CLI、登录和模型权限均已可用，发送失败后又收到过时的位置指引。

**证据：** [sessions.rs:1536](../src/app/sessions.rs#L1536) 的主空态只有标题、统计和热力图，添加操作在 [sidebar.rs:654](../src/app/sidebar.rs#L654)；[shell.rs:303](../src/app/shell.rs#L303) 依据空会话直接显示“已就绪”。[runtime.rs:338](../src/app/runtime.rs#L338) 指向“左下角设置”，实际设置位于 [shell.rs:679](../src/app/shell.rs#L679) 的右上标题栏。引擎页已正确区分启动文件、版本检测和认证，参见 `settings_provider_group`，主任务入口应采用同样口径。

**建议：** 在主空态提供“添加工作区”文字按钮，补充“检查 AI 引擎”次操作；有使用历史后再提高热力图权重。空会话改用“可以开始输入”等准确措辞，分别表达未检测、已找到 CLI、检测失败；认证未验证时不暗示已验证。错误提示直接提供“打开 AI 引擎设置”动作，避免依赖屏幕方位。

**验收：** 全新数据目录、未安装 CLI、错误路径、已找到 CLI 但未登录四种情况，都能看见下一步。普通用户无需先阅读使用指南即可添加工作区并定位配置问题；检查过程不自动发送收费的模型请求。

### HFE-09 · Git 禁用状态缺少一致的原因与恢复动作

**场景与影响：** 已填写提交说明且勾选文件，但某个后台会话仍在同一工作目录执行，提交按钮灰掉。用户需要猜测是选区、暂存、任务还是 Git 状态造成阻塞。

**证据：** [git_ui.rs:900](../src/app/git_ui.rs#L900) 将只读、忙碌、运行任务、刷新、集成操作、暂存范围等条件合并为禁用值；[git_ui.rs:1243](../src/app/git_ui.rs#L1243) 的提交提示只解释勾选范围，暂存操作提示也主要是文件数。AI 生成按钮已经使用 [generate_tip](../src/app/git_ui.rs#L913) 解释部分原因，可作为统一改进的起点。

**建议：** 将可执行性计算为结构化的原因，而非只返回 bool；在操作区常显最高优先级阻塞原因，并提供“查看运行会话”“暂存勾选文件”“刷新”等对应动作。合并/变基中和分离 HEAD 应给出明确处理方向。中文界面中的 Commit/Commit Message 可统一为“提交/提交说明”，保留必要 Git 术语。

**验收：** 无勾选、只有未暂存修改、空提交说明、同目录任务运行、刷新中、分离 HEAD、集成操作中、数据只读逐项验证。每个禁用状态都能解释原因；原因解除后按钮更新，不要求用户先尝试点击灰色按钮。

### HFE-10 · 编辑表单缺少未保存离开的处理

**场景与影响：** 用户修改较长 MCP/Skill 原生配置，或添加模型服务，未保存时按 Esc、点击关闭或取消。表单关闭后缺少找回刚才编辑内容的入口。偏好即时保存与表单显式保存虽然已有说明，长时间编辑仍容易误丢。

**证据：** [config_editor.rs:190](../src/app/settings/config_editor.rs#L190) 禁止点遮罩关闭，但未保存编辑仍允许键盘和关闭按钮；[config_editor.rs:323](../src/app/settings/config_editor.rs#L323) 取消直接关闭。[models.rs:443 · open_provider_editor](../src/app/settings/models.rs#L443) 也没有 dirty 离开处理，取消见 [models.rs:424](../src/app/settings/models.rs#L424)。这是表单尚未保存的内容，不是已经写入的配置丢失；现有格式校验、冲突检查和备份应继续保留。

**建议：** 按字段与初始值判断是否修改过，统一处理 Esc、关闭与取消。存在编辑时允许“继续编辑/放弃修改”，或在当前设置工作区保留未提交表单草稿；未修改时直接关闭。保存进行中保持现有阻止关闭机制。凭据字段不因表单恢复而新增明文落盘。

**验收：** 未编辑直接退出；编辑后 Esc/关闭/取消得到一致结果；继续编辑保留内容；明确放弃才清除。校验失败或外部文件冲突仍保留编辑内容，且不会误关闭整个设置工作区。

### HFE-11 · 排队行为与快捷键帮助不够可发现

**场景与影响：** 回复中输入第二条任务，右侧只显示停止；用户不知道 Enter 可以排队，鼠标用户也没有明确的“加入队列”操作。已有队列时的容量限制主要在再次发送后才得到解释。

**证据：** [runtime.rs:182](../src/app/runtime.rs#L182) 将运行中的发送转为排队；[composer.rs:682](../src/app/composer.rs#L682) 的同一位置则展示停止。输入占位只介绍任务和 `@`；[queue.rs:9](../src/app/queue.rs#L9) 已有阻塞原因，但输入区仅将结果转换为 busy。[settings.rs:517 · settings_shortcuts_page](../src/app/settings.rs#L517) 的快捷键页只列部分全局导航，未覆盖发送、换行、排队、文件内容查找与 Diff 跳转。

**建议（按 2026-11-06 界面反馈修订）：** 将“Enter 发送（运行中自动排队）· Shift+Enter 换行”放入输入框 placeholder；发送／停止图标保持原工具栏位置，不另起提示行或增加加入队列按钮。队列已满时沿用发送校验提示。保留 Ctrl+Enter 换行兼容性，在帮助中说明。快捷键帮助按当前区域分组，补全文件查找、Diff 和消息输入；文件搜索增加可见入口，不要求记住双击 Shift。

**验收：** 运行中 Enter 自动排队一条消息，第二条不覆盖已有内容；取回与停止语义清楚，输入区没有独立加入队列按钮。候选输入状态下 Enter 只确认中文，`@` 候选打开时先选择文件。帮助展示的快捷键与实际绑定一致。

| 编号 | 待验证风险与源码线索 | 操作与通过条件 |
| --- | --- | --- |
| V-01 | 窄窗的输入操作拥挤。默认导航 420px，输入区底部同一行包含新建、权限、用量、模型、附件、发送；模型名可占 170px。见 [shell.rs:9](../src/app/shell.rs#L9)、[composer.rs:636](../src/app/composer.rs#L636)、`composer_model_picker` | 在 850×500、1100×700、1200×800、1600×1000 的逻辑视口，组合长模型名、用量、附件、审批和队列；发送/停止、权限及关键状态均可达。已有导航收起到 38px、右栏窄窗覆盖模式，不能写成“没有响应式设计” |
| V-02 | 精细指针与文字缩放。附件移除 18×18、添加工作区 22×22、新会话高 22、权限选择高 22。见 [composer.rs:385](../src/app/composer.rs#L385)、[sidebar.rs:654](../src/app/sidebar.rs#L654)、`permission_picker` | 在 100%/150%/200% DPI、触控板和系统文本放大下检查真实命中区域、间距与误点。以不小于 24×24 逻辑像素作为桌面项目目标，重要操作优先 28–32；触摸场景另扩大。不能只因视觉尺寸小于 44 就判不合格 |
| V-03 | UI Automation / Narrator 对虚拟列表、选中态、通知和加载状态的表达 | 从启动到会话、审批、Git、设置全程只用键盘与 Narrator；能读出名称、角色、状态和错误；焦点不落到被覆盖或已卸载内容 |

| V-05 | 长会话与多后台任务时的注意力和响应 | 使用长正文、多代码块、Mermaid、多个并行任务；检查阅读时不抢焦点、离开末尾后不自动拉回、停止有立即反馈；记录输入和滚动延迟，不用本轮静态审查声称性能达标 |
| V-06 | 启动等待与关闭运行任务的可理解性 | 大历史库和慢路径下计时，确认最迟超时能返回工作台、保留既有会话且可重新导入；关闭前有多个运行任务时评估是否需要“继续工作/停止并退出”的选择。现有关闭会取消任务，不应仅凭此推断取消实现错误 |
| V-07 | 持续动画和状态颜色依赖。运行/未读点均重复透明度动画，见 [components.rs:20](../src/app/components.rs#L20) | 检查系统减少动画设置是否由 GPUI 链路生效；若未生效，提供静态替代。灰度下能区分运行、待审批、失败和未读；不能仅从应用未显式读取偏好推断底层库不支持 |
| V-08 | 弹窗与右栏遮挡、长路径及超长错误 | 在短窗口打开设置编辑、模型选择、审批详情、文件 Diff 和通知；焦点可见，Esc 只关闭最上层，长内容可滚动/复制，操作栏不被挤出。右栏覆盖聊天时仍有清楚的关闭与返回路径 |

## 5. 分批实施与验收安排

| 批次 | 目标 | 纳入问题 | 建议实现范围 | 退出条件 |
| --- | --- | --- | --- | --- |
| A | 保住输入成果，让关键操作能被正确决定与执行 | HFE-01/02/03/04 | 草稿存储与退出；共享动作按钮；审批摘要；Diff 比较范围 | 四项对应场景通过，原有发送保存屏障、审批隔离、Git 选区语义不回退 |
| B | 减少高频切换、键盘操作和状态判断成本 | HFE-05/06/07/09/11 | 会话阅读锚点；列表焦点；主题 token；操作禁用原因；状态提示与帮助 | 键盘主流程完整、两主题可读、往返会话不丢阅读位置 |
| C | 改善首次使用和配置编辑，完成桌面组合验收 | HFE-08/10、V-01～V-08 | 空态引导；准确状态与跳转；表单 dirty 处理；必要的自适应布局 | 新用户路径可完成，实机矩阵有记录；未通过项目继续保留开放状态 |

以上批次是依赖与价值顺序，不是工期估算。AI 设置管理的后续结构调整与本报告的 HFE-08/10 应共同验收，参见 [AI 设置专项完善](ai-settings-management-design.md)，避免两个入口对同一配置状态使用不同措辞。

实施前先记录以下基线；本轮没有采集这些指标：

| 任务 | 建议记录 | 验收意图 |
| --- | --- | --- |
| 初次配置后发送第一条任务 | 完成率、卡住位置、求助次数 | 找得到工作区与引擎配置入口 |
| 运行中停止当前任务 | 控件发现时间、输入到可见反馈的时间、是否误停其他会话 | 关键控制明确且对象正确 |
| 处理工具审批 | 能否复述操作与范围、是否需要打开协议原文 | 以可理解信息作决定 |
| 部分暂存文件的提交 | 用户预计提交内容与实际结果是否一致 | 可见预览与操作后果一致 |
| A/B 会话交替阅读 | 找回原位置的次数、额外滚动量 | 降低恢复上下文的成本 |
| 正常退出后继续编辑 | 草稿与附件恢复率、误发送次数 | 已输入内容可恢复且保持用户控制 |

每个功能批次只增加与行为相关的测试：草稿恢复检查实际落盘与重启；Git 检查真实暂存版本；会话阅读检查锚点；键盘与焦点使用 GPUI UI 测试。之后补真实 Windows 的输入法、读屏、DPI 和多屏验证，不能用测试通过代替操作体验。

建议的最终验收记录逐行包含：构建 SHA、模式（默认 GPUI / Shell 开发构建）、视口/DPI、主题、测试数据、步骤、结果和证据位置。真实 CLI 验收与合成运行分开记录；没有执行的项目保持“未验证”。
